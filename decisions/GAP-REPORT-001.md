# GAP-REPORT-001 — تحلیل فنی BUILD-SPEC v1.0

> **مرجع:** BUILD-SPEC v1.0 · **نویسنده:** Owner فنی (Claude Opus 5) · **تاریخ:** 2026-07-28
> **مبنای قرارداد:** §۲۰ بند ۷ — «هر جای این سند که با واقعیت ابزارها نمی‌خواند، صریح بگو و جایگزین پیشنهاد بده. سکوت کردن روی شکاف = نقض قرارداد.»
> **وضعیت:** این سند ورودی اجباری BUILD-SPEC v2.0 است. هر GAP یا بسته شده، یا به TRADEOFF-REGISTER منتقل شده است.

## ۰) ارزیابی کلی سند v1.0

سند v1.0 از نظر مهندسی **بالاتر از میانگین اسناد agentic** است. این‌ها را درست انجام داده و در v2.0 دست‌نخورده می‌مانند:

| نقطه قوت | چرا مهم است |
|---|---|
| Event sourcing + append-only + compaction | replay، audit، و بازسازی وضعیت بدون اتکا به حافظهٔ انسان |
| Receipt به‌عنوان شرط Done | تنها راه عملی برای اثبات «کار انجام شد» در سیستم بی‌حالت |
| Lease با **fencing token** | آگاهی نویسنده از split-brain — این را اکثر اسناد جا می‌اندازند |
| Autonomy Ratchet | تفاوت بین «اتوماسیون» و «سیستم خودمختار» |
| Succession Protocol | تشخیص درست اینکه bus-factor قاتل اصلی سیستم‌های agentic است |
| TRADEOFF-REGISTER (I8) | صداقت مهندسی: «trade-off صفر» را رد کرده |
| Separation of duties (هیچ ایجنتی خودش را تأیید نمی‌کند) | جلوگیری از حلقهٔ خودتأییدی |

**اما:** سند یک **قرارداد داده و پروتکل** خوب است و یک **طرح سیستم عامل** ناقص. سه شکاف ساختاری دارد که اگر بسته نشوند، ادعای «۷۲ ساعت بدون انسان» قابل اثبات نیست:

1. **بستر اجرا (compute substrate) تعریف نشده** — نوشته «چه» اجرا شود، ننوشته «کجا» زنده می‌ماند.
2. **مکانیزم‌های ایمنی fail-open هستند** — kill switch به SaaS خارجی وابسته است.
3. **راهی برای اثبات ۷۲ ساعت در کمتر از ۷۲ ساعت وجود ندارد** — هیچ محیط شبیه‌سازی تعریف نشده.

مجموع: **۱۹ GAP** — ۶ مورد `blocker`، ۹ مورد `major`، ۴ مورد `minor`.

## ۲) GAPهای Blocker

### G1 — بستر اجرا تعریف نشده؛ A2A Gateway یک SPOF ساخته است
**شکاف.** §۵ می‌گوید Gateway = FastAPI + Postgres + Redis + mTLS. سند هرگز نمی‌گوید این کجا اجرا می‌شود، چه کسی deploy می‌کند، چه کسی monitor می‌کند، و **اگر Gateway بخوابد چه می‌شود**. طبق §۲.۱ کل L3 از Gateway می‌گذرد؛ پس Gateway down = هیچ ایجنتی با ایجنت دیگر حرف نمی‌زند = «۷۲ ساعت خودمختار» شکست می‌خورد. Gateway هم‌زمان *مسیر داده* و *مسیر کنترل* است — یک SPOF کلاسیک.

**اصلاح (v2.0 §۵).** **Dual-transport با تنزل تدریجی:**

```
T1  git-transport   (baseline, همیشه کار می‌کند)
    A2A task = یک فایل JSON در state/a2a/inbox/{agent}/{ulid}.json + commit
    trigger  = GitHub Actions (repository_dispatch / push path filter) یا Moxt cron
    latency  ~30–90s · durability عالی · audit رایگان و ذاتی · هزینهٔ زیرساخت صفر
T2  moxt-transport  (fast path بومی، بدون host خارجی)
    A2A task = Task در Moxt Workflow، assign به AI Teammate → pipeline آن ایجنت trigger می‌شود
    latency  ~ثانیه · بدون سرور · approval و human-in-the-loop بومی
T3  http-transport  (اختیاری، فقط برای مقیاس)
    همان Gateway §۵ — اما **کش/بهینه‌سازی latency**، نه منبع حقیقت
```

قانون سخت: **هیچ قابلیت ایمنی‌ای نباید فقط روی T3 زنده باشد.** Gateway باید بتواند بمیرد و سیستم با تنزل latency (نه توقف) ادامه دهد. Health check هر ۶۰ ثانیه؛ ۳ خطای پیاپی → fallback خودکار به T1.

> **بینش کلیدی:** در Moxt، «assign کردن یک Task به یک AI Teammate» *خودش* یک A2A dispatch bus است — با صف، مالکیت، وضعیت، تاریخچه و مسیر تأیید انسانی. یعنی VS-2 بدون نوشتن حتی یک خط FastAPI قابل تحویل است. Gateway به VS-11 (اختیاری، مبتنی بر مقیاس) منتقل می‌شود.

### G2 — طراحی برای «چند انسان» در یک سازمان تک‌نفره
**شکاف.** §۱۱.۲: «Two-key rule: هر مسیر بحرانی حداقل دو مالک دارد (یک ایجنت + یک انسان یا دو ایجنت مستقل)». §۱۵: CODEOWNERS + protected main. §۱۱.۲ dead-man switch: اگر Owner ۷۲ ساعت پاسخ ندهد… — **همهٔ این‌ها فرض می‌کنند بیش از یک انسان وجود دارد.** واقعیت: bus-factor = ۱. با یک نفر، CODEOWNERS یعنی «خودت PR خودت را approve کن» = تئاتر امنیتی، و protected main یک اصطکاک بی‌فایده می‌شود.

**اصلاح (v2.0 §۱۱).** پذیرش صریح مدل **Solo-Operator + Agent Fleet**:
- **Two-key = دو ایجنت با تبار مستقل.** «مستقل» تعریف عملیاتی می‌شود: مدل متفاوت یا prompt-lineage متفاوت + دسترسی به شواهد خام به‌جای خروجی ایجنت اول + وظیفهٔ صریح **رد کردن** (adversarial reviewer، نه تأییدکننده). یک ایجنت که همان مدل و همان context را دارد، یک کلید دوم نیست — یک آینه است.
- **CODEOWNERS واقعی:** انسان مالک ۴ مسیر است و بس: `configs/pricing/**`، `**/ToS*`، `infra/terraform/**`، `security/iam/**`. بقیه مالک ایجنتی دارند با gate ایجنت مستقل.
- **Escrow بازیابی برای غیرمتخصص:** یک `RECOVERY.md` + بستهٔ رمزنگاری‌شده که یک نفر **غیرفنی** بتواند با آن سیستم را متوقف یا واگذار کند. bus-factor ۱ فقط با یک مسیر خروج انسانی مهار می‌شود، نه با ایجنت بیشتر.
- **کانال خارج از باند:** hard requirement. Slack/Telegram — چون اگر Moxt و GitHub هر دو در دسترس نباشند، Owner هیچ راهی برای شنیدن alert ندارد.

### G3 — Kill Switch به‌صورت fail-open طراحی شده
**شکاف.** §۶.۳: فعال‌سازی kill switch «از ClickUp (تغییر وضعیت یک تسک مشخص)». یعنی **مکانیزم توقف اضطراری روی یک SaaS پرداختی خارجی با یک token قابل‌انقضا سوار است.** سه حالت شکست فاجعه‌بار:
1. token ClickUp منقضی شود → نمی‌توانی سیستم را متوقف کنی.
2. ClickUp API down باشد → همان.
3. Orchestrator نتواند وضعیت kill switch را بخواند → سند نمی‌گوید چه کند. رفتار پیش‌فرض هر پیاده‌سازی ساده: «فرض کن false است و ادامه بده» = **fail-open**. این بدترین حالت ممکن است.

**اصلاح (v2.0 §۶.۳).** **Kill switch چندمسیره و fail-closed:**

```
مسیرهای فعال‌سازی (OR — هر کدام کافی است):
  K1  فایل state/KILL در repo (منبع اصلی، atomic، نسخه‌دار)
  K2  GitHub repository variable KILL_SWITCH=global|scoped:...
  K3  وضعیت Task در Moxt Workflow «Control Room / Kill Switch»
  K4  CLI: scripts/killswitch.py (مسیر محلی، بدون شبکه)
  K5  خودکار توسط Orchestrator: نقض SLO بحرانی، هزینه > ۳× baseline،
      الگوی خطای غیرعادی، هشدار امنیتی، یا **گم شدن ۳ heartbeat**

قانون fail-closed (اجباری):
  اگر یک worker نتواند وضعیت kill switch را از **حداقل یک** مسیر
  معتبر با timestamp تازه‌تر از ۱۵ دقیقه بخواند
  → همهٔ عملیات با blast radius > L3 متوقف می‌شود (halt، نه continue).
  «نمی‌دانم» هم‌ارز «متوقف شو» است، نه هم‌ارز «مجاز است».
```

اضافه: `scripts/killswitch.py --verify` که هر شبانه در CI اجرا می‌شود و **عملاً** هر ۵ مسیر را تست می‌کند. kill switch تست‌نشده = kill switch وجود ندارد.

### G4 — کلید Idempotency از نظر معنایی غلط است
**شکاف.** §۳.۵: `idempotency_key = sha256(from|to|capability|inputs_hash)`. این کلید **زمان ندارد**. پس:
- `analytics.query_metric` روی همان بازه، ۶ ساعت بعد → پاسخ کش‌شدهٔ کهنه برمی‌گردد. سیستمی که SENSE آن کهنه است، کور است.
- `qa.gate.run` روی همان artifact بعد از تغییر *محیط* (نه artifact) → «pass» قبلی برمی‌گردد در حالی که الان fail است.
- retry مشروع پس از یک شکست گذرا، از retry تکراری قابل تفکیک نیست.

**اصلاح (v2.0 §۳.۵).** تفکیک صریح سه کلاس idempotency، به‌ازای هر capability در Agent Card:

```yaml
idempotency:
  qa.gate.run:          {class: scoped,   ttl: 15m,  key: [from,to,cap,inputs_hash,env_epoch]}
  cfg.publish.canary:   {class: forever,  key: [cap,artifact_hash,target_epoch]}
  analytics.query:      {class: none,     cache_ttl: 60s}
```
- `forever` — عملیات جهش‌دهنده و غیرقابل‌تکرار (deploy، پرداخت). کلید شامل `target_epoch` است تا انتشار مجدد آگاهانه ممکن باشد.
- `scoped` — نتیجه در پنجرهٔ TTL معتبر است.
- `none` — خواندنی؛ کش کوتاه، هرگز idempotency ماندگار.

بدون این تفکیک، سیستم یا کار را دوباره انجام می‌دهد (خطرناک) یا داده کهنه می‌خواند (کور) — و سند v1.0 راهی برای انتخاب نداده است.

### G5 — Invariant «Receipt completeness = ۱۰۰٪ همیشه» ارضاناپذیر است
**شکاف.** I3 + §۱۴: «هیچ کار بدون receipt» و «Receipt completeness ۱۰۰٪ — نقض = build شکست». اما اگر یک ایجنت **وسط کار crash کند** (که §۱۶ خودش در تست Chaos به‌عنوان سناریوی الزامی می‌خواهد)، تسکِ شروع‌شده هرگز receipt نمی‌گیرد. نتیجه: build برای همیشه قرمز می‌ماند. سرنوشت قطعی چنین gate‌ای: در هفتهٔ دوم خاموش می‌شود — و با آن، کل مکانیزم auditability فرو می‌ریزد.

**اصلاح (v2.0 §۳.۳).** `receipt.status` اجباری با ۵ مقدار و یک reaper:

```
complete   | کار تمام، verify سبز
failed     | کار تمام، نتیجه منفی — receipt کامل و معتبر است
abandoned  | لغو آگاهانه، دلیل ثبت‌شده
crashed    | tombstone که reaper نوشته (lease منقضی + بدون receipt)
superseded | تسک جدیدی جایگزین شد، اشاره به جانشین
```
- KPI بازنویسی می‌شود: **«۱۰۰٪ تسک‌ها receipt دارند»** (هر status)، به‌علاوهٔ یک KPI مستقل: **`crash_rate < 2%`**.
- `hooks/task_complete.py` عدم وجود receipt را رد می‌کند؛ reaper (heartbeat هر ۱۵ دقیقه) tombstone می‌نویسد. یک invariant قابل‌اجرا جای یک invariant اخلاقی را می‌گیرد.

### G6 — `seq` سراسری صعودی با CAS روی GitHub ناپایدار است
**شکاف.** §۳.۲: «`seq` یکنواخت صعودی با CAS روی فایل روز». با ۵ ایجنت موازی (§۱۲.۱ گام ۵) که همه به `state/events/YYYY-MM-DD.ndjson` می‌نویسند، CAS روی git = رد شدن push، خواندن مجدد، شماره‌گذاری مجدد، تلاش مجدد. زیر بار، این تبدیل به retry storm می‌شود و throughput به یک نویسنده در هر round-trip می‌رسد. **و ترتیب کلی (total order) اصلاً لازم نیست** — سند خودش `correlation_id` و `causation_id` دارد، یعنی چیزی که واقعاً نیاز است ترتیب علّی است.

**اصلاح (v2.0 §۳.۲).** `seq` سراسری حذف می‌شود:
- `event_id` = **ULID** → مرتب‌شدنی بر اساس زمان، بدون هماهنگی.
- `actor_seq` = شمارندهٔ یکنواخت **به‌ازای هر actor** → تشخیص گم‌شدن event برای هر actor.
- ترتیب علّی از `causation_id` (زنجیرهٔ موجود) استنتاج می‌شود.
- **پارتیشن نوشتن:** `state/events/{date}/{actor}.ndjson` — هر actor فقط فایل خودش را می‌نویسد ⇒ **merge conflict به‌طور ساختاری ناممکن می‌شود**، نه اینکه مدیریت شود.

این تنها جایی نیست که این الگو جواب می‌دهد: همان قانون «یک نویسنده به ازای هر مسیر» با `owns` در Agent Card ترکیب می‌شود و در `hooks/pre_tool.py` اجبار می‌گردد ⇒ کل کلاس تعارض git از سیستم حذف می‌شود.

### G7 — هیچ محیط شبیه‌سازی وجود ندارد؛ پس VS-10 قابل اثبات نیست
**شکاف.** VS-10 DoD: «۷۲ ساعت اجرای بدون مداخله». §۱۶ تست Chaos: «کشتن ایجنت وسط کار، انقضای lease، قطع provider». §۱۱.۲: «cold restore drill ماهانه». **هیچ‌کدام بدون یک محیط تست قابل اجرا نیستند** و سند هیچ محیطی تعریف نمی‌کند. پیامد عملی: این تست‌ها روی کاربران واقعی Marzneshin اجرا می‌شوند، یا — به‌احتمال بیشتر — هرگز اجرا نمی‌شوند و DoD با یک ادعا امضا می‌شود. علاوه بر این، هر چرخهٔ اشکال‌زدایی حلقهٔ ۳۰ دقیقه‌ای، ۳۰ دقیقه طول می‌کشد.

**اصلاح (v2.0 §۱۶ + `sim/`).** **Deterministic Simulation Harness** — بالاترین بازده در کل این بازنگری:

```
sim/
├─ clock.py          ساعت مجازی — ۷۲ ساعت در < ۶۰ ثانیه اجرا می‌شود
├─ world.py          دنیای شبیه‌سازی: nodes، کاربران، funnel، درآمد، حادثه
├─ fakes/            پیاده‌سازی fake همهٔ Adapterها با همان contract test
├─ scenarios/        سناریوهای YAML: node_outage، payment_provider_down،
│                    agent_crash_mid_task، lease_expiry، cost_spike،
│                    prompt_injection، metric_gaming، clickup_down، gateway_down
├─ chaos.py          تزریق خطا با seed → قابل بازتولید دقیق
└─ report.py         خروجی امتیازدار: MTTR، کار تکراری، receipt کامل، نقض guardrail
```

قواعد اجباری:
- **هیچ کد نویی وارد مسیر production نمی‌شود مگر ابتدا در `sim/` سبز شود.**
- هر باگ production یک سناریوی رگرسیون در `sim/scenarios/` می‌سازد.
- `seed` در receipt ثبت می‌شود ⇒ هر شکست دقیقاً بازتولیدشدنی است.
- CI شبانه: کل مجموعهٔ سناریو با ۱۰ seed تصادفی.

این تنها راه اثبات صادقانهٔ «۷۲ ساعت خودمختار» **قبل از** ریسک‌کردن کاربر واقعی است.

## ۳) GAPهای Major

### G8 — بودجهٔ توکن با ریاضیات نمی‌خواند
**شکاف.** §۳.۴ برای *یک* ایجنت Tier 2: `tokens_per_day: 300000, usd_per_day: 8`. §۱۲.۱: tick هر ۳۰ دقیقه (۴۸ بار در روز)، هر tick تا ۵ ایجنت موازی. §۱۰: ۱۷ ایجنت. ۱۷ × ۳۰۰k = ۵.۱M توکن در روز. با قیمت‌گذاری مدل رده‌بالا، `usd_per_day: 8` دو مرتبهٔ بزرگی خطا دارد. سند سقف دارد اما **مدل هزینه ندارد** — و tick مبتنی بر polling است: ۴۸ بار در روز SENSE می‌کند حتی وقتی هیچ چیز تغییر نکرده.

**اصلاح (v2.0 §۶.۴).**
- **دفتر بودجهٔ سلسله‌مراتبی:** workspace → tier → agent → task. رزرو *قبل* از اجرا، تسویه بعد. `budget` سطح tier سخت‌گیرانه‌تر از جمع سطح agent است (over-subscription کنترل‌شده).
- **مسیریابی مدل بر اساس نوع کار:** classify/extract/SENSE با مدل ارزان؛ مدل رده‌بالا فقط برای DECIDE، طراحی، بازبینی خصمانه. ثبت `model` در هر receipt تا leverage قابل اندازه‌گیری شود.
- **tick تطبیقی، رویدادمحور:** trigger اصلی = رویداد واقعی (webhook، alert، تغییر متریک بیش از آستانه). polling فقط به‌عنوان کف امنیتی: ۳۰ دقیقه در حالت فعال → backoff نمایی تا ۴ ساعت وقتی N tick پیاپی «تغییر معنادار» نداشتند. یک SENSE ارزان (فقط هش متریک‌ها) دروازهٔ tick گران است.
- **`budget_forecast`:** پیش‌بینی روزانه؛ در ۸۰٪ escalate، در ۱۰۰٪ kill switch از نوع `budget`.

### G9 — بودجهٔ ۳ ثانیه‌ای hook با کار خواسته‌شده جمع نمی‌شود
**شکاف.** §۷.۲: «هر hook باید < ۳ ثانیه اجرا شود». اما PreCommit باید انجام دهد: «نبود task ID، **تست قرمز**، CODEOWNERS، gitleaks، receipt ناقص». اجرای مجموعهٔ تست در ۳ ثانیه ناممکن است.

**اصلاح (v2.0 §۷.۲).** hookها دو ردهٔ زمانی می‌گیرند:
- **رده A (< ۳s، local, blocking):** بررسی‌های ساختاری — task ID، schema فایل‌های تغییریافته، `owns`/lease، gitleaks **فقط روی staged diff**، کامل بودن فیلدهای receipt.
- **رده B (< ۹۰s، pre-push یا CI):** مجموعهٔ تست، contract test، سناریوهای `sim/`، SAST، policy test.
- هر hook باید **بدون شبکه** کار کند (I/O شبکه در hook = دلیل شمارهٔ یک flakiness).

### G10 — دفاع Prompt Injection بیان شده، معماری نشده
**شکاف.** §۱۵ می‌گوید محتوای خارجی «به‌عنوان داده برچسب می‌خورد نه دستور» و «ایجنت‌ها هرگز capability را از محتوای ورودی نمی‌گیرند». این‌ها اهداف درستی هستند اما **هیچ مکانیزمی** برای اجبارشان تعریف نشده. یک ایجنت پشتیبانی که تیکت می‌خواند، بدون رد کردن آلودگی (taint) در سراسر مسیر، هیچ راهی برای تشخیص «این جمله از کاربر آمده» ندارد.

**اصلاح (v2.0 §۱۵.۲).** **Taint tracking در A2A envelope:**
```json
"input_provenance": [
  {"field":"$.ticket.body","source":"support:zendesk#8123",
   "trust":"untrusted","sanitizer":"envelope-v1","content_hash":"sha256:..."}
]
```
- سه سطح اعتماد: `owner` > `internal` > `untrusted`.
- **قانون سخت:** فراخوانی هر ابزار جهش‌دهنده که پارامترش از یک فیلد `untrusted` مشتق شده، به Policy Engine می‌رود و **حداکثر L1** می‌گیرد — بدون استثنا.
- capability grant توسط منبع اعتماد (Gateway/T1) **امضا** می‌شود و از payload مشتق نمی‌شود.
- محتوای خارجی همیشه در envelope با مرز صریح: `<<UNTRUSTED_DATA source=... >> … <<END>>`.
- مجموعهٔ تست injection در `sim/scenarios/prompt_injection.yaml` — معیار پذیرش §۱۶: صفر یافتهٔ high.

### G11 — تکامل schema بدون مکانیزم مهاجرت
**شکاف.** `schema_version` در همه‌جا هست، اما هیچ‌جا نمی‌گوید وقتی v1.0 → v2.0 شد با ۳ ماه event قدیمی چه می‌شود. سیستمی که event sourcing دارد و upcaster ندارد، پس از اولین breaking change قابلیت replay را از دست می‌دهد — یعنی همان چیزی که کل ارزش event sourcing است.

**اصلاح (v2.0 §۳.۷).** `analytics/schemas/migrations/` با upcasterهای **تابع خالص** `v1_0__v1_1.py`. قواعد: خواننده باید همهٔ نسخه‌های تاریخی را بخواند · compaction هرگز event خام را بازنویسی نمی‌کند · هر تغییر schema یک تست round-trip روی نمونه‌های واقعی آرشیو دارد · CI روی حذف فیلد بدون upcaster شکست می‌خورد.

### G12 — «canary سبز» بدون قدرت آماری، نویز است
**شکاف.** VS-5: canary ۱٪ → probe → auto-rollback. §۱۴: CSR ≥ ۹۸٪. اما: probe از کجا؟ چند نمونه؟ در ۱٪ ترافیک و پنجرهٔ ۳۰ دقیقه، تعداد نمونه ممکن است چند ده باشد؛ تفکیک ۹۸٪ از ۹۶٪ در آن حجم آماری غیرممکن است. «canary سبز ۳۰ دقیقه» (§۶.۱) بدون حداقل حجم نمونه، یک سکهٔ شیر-یا-خط با ظاهر مهندسی است.

**اصلاح (v2.0 §۵-config).** **canary = experiment.** یک موتور، دو کاربرد:
- gate ارتقا نیازمند `n_min` محاسبه‌شده از اندازهٔ اثر قابل‌تشخیص (MDE) و همان توان آماری §۱۳.۴ (power ۰.۸، alpha ۰.۰۵).
- **sequential test با always-valid p-value** برای توقف زودهنگام ایمن — دقیقاً همان ابزاری که سند برای آزمایش‌ها خواسته، اینجا هم استفاده می‌شود.
- اگر `n < n_min`: وضعیت `inconclusive` → **ماندن در همان مرحله**، نه ارتقا. «داده کافی نیست» هرگز به «سبز» ترجمه نمی‌شود.
- **مشخصات ناوگان probe:** حداقل ۳ شبکهٔ مستقل (ASN متفاوت)، فاصلهٔ نمونه‌گیری، مسیر گزارش، و رفتار در صورت down بودن خود probe (fail-closed: بدون probe سالم، ارتقا ممنوع).

### G13 — هیچ محافظی در برابر metric gaming (قانون گودهارت) نیست
**شکاف.** سند در برابر شکست *فنی* بسیار خوب محافظت می‌کند و در برابر **موفقیت در متریک غلط** هیچ. Lifecycle Growth Agent با KPI `activation_rate` می‌تواند با اسپم کردن، عدد را بالا ببرد. `unsubscribe_rate` در KPI هست، اما **همان ایجنت مالک آن است** — یعنی ایجنتی که انگیزهٔ گیم کردن دارد، نگهبان خودش است. این همان الگویی است که §۱۰ در «هیچ ایجنتی خودش را تأیید نمی‌کند» رد کرده، اما در سطح متریک اعمال نشده.

**اصلاح (v2.0 §۱۰.۴).** **Counter-metric اجباری با مالکیت متقابل:**
```yaml
kpi:         [activation_rate, trial_to_paid]
counter_kpi: [unsubscribe_rate, support_contact_per_user, refund_rate]
counter_kpi_owner: trust-compliance   # مالک متفاوت — اجبار در CI
```
CI رد می‌کند اگر `counter_kpi_owner == id`. به‌علاوه یک job ماهانهٔ «red-team the metrics»: یک ایجنت خصمانه تلاش می‌کند نشان دهد هر KPI **بدون** ایجاد ارزش واقعی چگونه قابل بالا بردن است؛ خروجی → backlog guardrail.

### G14 — ترکیب Tier و مسیر ساخت ۱۷ ایجنت
**شکاف.** §۱۰ ترتیب ساخت درستی می‌دهد (Tier 0 اول) اما: (الف) هیچ **Data/Analytics Engineer** در هیچ Tier نیست، در حالی که VS-7/VS-9 کل taxonomy رویداد و مدل‌های unit-economics را می‌خواهند؛ (ب) QA Gate «تأیید خودش روی کار خودش» ممنوع است، اما **چه کسی تعریف gateهای QA را بازبینی می‌کند؟** (ج) Handoff Guardian در Tier 1 است، در حالی که «هیچ جلسه‌ای بدون HANDOFF» (قانون آهنین ۳) از VS-1 لازم است.

**اصلاح (v2.0 §۱۰).**
- **Handoff Guardian به Tier 0 منتقل می‌شود** — بدون آن، قانون آهنین ۳ از روز اول قابل اجبار نیست.
- **Analytics Engineer به Tier 1 اضافه می‌شود** (پیش‌نیاز VS-7).
- **Adversarial Reviewer** به‌عنوان یک نقش برشی (cross-cutting) در Tier 0: تبار مستقل، تنها وظیفه‌اش رد کردن است؛ کلید دومِ two-key و بازبین gateهای QA.
- Tier 0 از ۵ به **۷** می‌رسد. ۱۷ → ۱۹ ایجنت در نقشهٔ کامل، اما ترتیب ساخت سخت‌گیرانه‌تر: Tier 0 کامل و سبز، بعد Tier 1.

### G15 — ترتیب Vertical Slice ریسک را در جای غلط می‌گذارد
**شکاف.** §۱۷: VS-3 (Control Room) قبل از VS-4 (ایجنت‌ها) → طراحی فیلدهای UI قبل از دانستن نیاز واقعی ایجنت‌ها = بازکاری. مهم‌تر: **VS-6 (Continuity) بعد از VS-5 (Config Pipeline)** — یعنی سیستم روی کاربران واقعی Marzneshin config منتشر می‌کند **قبل از اینکه succession، dead-man switch و cold restore ثابت شده باشند**. این ترتیب ریسک را وارونه کرده.

**اصلاح (v2.0 §۱۷).**
```
VS-1  Spine                    (بدون تغییر)
VS-2  Simulation Harness       ← جدید و زودهنگام؛ همهٔ تست‌های بعدی روی آن سوار است
VS-3  A2A over T1/T2           (بدون FastAPI؛ Gateway → VS-11 اختیاری)
VS-4  Continuity + Kill Switch ← از VS-6 به جلو آمد: قبل از هر تماس با production
VS-5  Tier 0 Agents (۷ ایجنت)
VS-6  Control Room             ← عقب رفت: بعد از اینکه می‌دانیم ایجنت‌ها چه فیلدی لازم دارند
VS-7  Config Pipeline          اولین تماس با کاربر واقعی — و اکنون continuity ثابت‌شده است
VS-8  Growth Spine
VS-9  Experiment Loop
VS-10 Revenue Command Center
VS-11 Autonomy Ratchet + Shadow Mode
VS-12 (اختیاری) HTTP Gateway — فقط اگر latency T1/T2 محدودکننده شد
```
قاعدهٔ حاکم بدون تغییر می‌ماند: **هیچ‌وقت دو اسلایس هم‌زمان.**

### G16 — حلقهٔ §۱۲.۱ به داده‌ای نیاز دارد که تا VS-8 وجود ندارد
**شکاف.** گام SENSE می‌خواهد «SLO، funnel، revenue، tickets، error budget، هزینه» را بخواند. funnel و revenue تا VS-8 (Growth Spine) وجود ندارند. پس حلقهٔ اتوماسیون در فاز اول یا crash می‌کند یا با داده تقلبی کار می‌کند — و هیچ‌کدام در سند تصریح نشده.

**اصلاح (v2.0 §۱۲.۰).** حلقه **مرحله‌ای** می‌شود، با اعلام صریح توانایی:
```
Tick-A (از VS-1): وضعیت مخزن، lease، receipt، هزینهٔ توکن، سلامت CI
Tick-B (+VS-7):   + SLO، CSR، probe، error budget
Tick-C (+VS-8):   + funnel، activation، درآمد
Tick-D (+VS-9):   + خوانش آزمایش، autonomy ratchet
```
هر tick سطح خود را در event ثبت می‌کند. اگر ورودی لازم غایب باشد → `degraded_sense` ثبت می‌شود و تصمیم‌های وابسته به آن ورودی **مسدود** می‌شوند؛ حدس زدن ممنوع است.

## ۴) GAPهای Minor

### G17 — Autonomy Ratchet شواهد ضعیفی دارد
§۶.۲: «۳۰ اجرای متوالی بدون rollback → پیشنهاد ارتقا». مشکل: در L1، هر اجرا انسان را در حلقه دارد؛ پس ۳۰ اجرای موفق چیزی دربارهٔ رفتار سیستم **بدون** انسان ثابت نمی‌کند. این شواهد برای ادعایی که می‌سازد کافی نیست.

**اصلاح:** **Shadow Mode.** ایجنت در سطح L(n) کار می‌کند اما تصمیمی که در L(n+1) می‌گرفت را هم ثبت می‌کند (بدون اجرا). ارتقا نیازمند: ۳۰ اجرای پاک **به‌علاوهٔ** ≥۹۵٪ توافق میان تصمیم سایه و تصمیم تأییدشدهٔ انسان، در ≥۲۰ نمونه، **به‌علاوهٔ** سبز بودن سناریوهای `sim/` مربوطه. این ratchet را از «امیدواری آماری» به «شواهد counterfactual» ارتقا می‌دهد.

### G18 — زنجیرهٔ receipt دستکاری‌پذیر است
receiptها فایل‌های JSON مستقل‌اند. یک ایجنت با دسترسی نوشتن می‌تواند receipt گذشته را بازنویسی کند و git history تنها ردیاب است.

**اصلاح:** **زنجیرهٔ هش‌شدهٔ receipt** — هر receipt شامل `prev_receipt_hash` (به‌ازای هر workstream) → audit log ضد‌دستکاری با هزینهٔ تقریباً صفر. `scripts/verify.py --chain` صحت زنجیره را در CI بررسی می‌کند. اختیاری برای فاز بعد: امضای cosign/age روی receipt.

### G19 — نقطهٔ کور حقوقی و انطباق
سند به‌درستی «ذخیرهٔ محتوای ترافیک و مقصد کاربر ممنوع» را می‌گذارد (§۱۳.۱) و «تغییر ToS» را انسانی نگه می‌دارد. اما برای یک کسب‌وکار در این دامنه، هیچ **playbook درخواست قانونی**، هیچ موضع صریح دربارهٔ حوزهٔ قضایی/محل داده، و هیچ ثبت انطباقی برای مسیر پرداخت وجود ندارد.

**اصلاح:** `security/compliance/` شامل: register انطباق، playbook درخواست قانونی (چه کسی پاسخ می‌دهد، چه چیزی وجود دارد و چه چیزی ندارد، چه چیزی هرگز ثبت نمی‌شود)، جدول محل داده به‌ازای هر Adapter، و بازبینی انطباق مسیر پرداخت. **همهٔ این‌ها L0 هستند — فقط پیشنهاد، تصمیم انسانی.**

## ۶) خلاصهٔ اجرایی — پنج تغییر ساختاری v1.0 → v2.0

1. **Gateway از مسیر بحرانی خارج می‌شود.** transport سه‌لایه با تنزل تدریجی؛ baseline رایگان و بدون host. SPOF حذف، و VS اول‌ها بدون هیچ زیرساخت خارجی تحویل‌شدنی می‌شوند.
2. **Simulation harness به VS-2 می‌آید.** ۷۲ ساعت در ۶۰ ثانیه، با seed و قابل بازتولید. تنها راه صادقانهٔ اثبات خودمختاری بدون ریسک‌کردن کاربر واقعی.
3. **Continuity و kill switch قبل از production می‌آیند** و fail-closed می‌شوند. «نمی‌دانم» = «متوقف شو».
4. **Solo-operator به‌صورت صریح طراحی می‌شود.** two-key = دو تبار مستقل با نقش خصمانه + escrow بازیابی برای غیرمتخصص.
5. **Ratchet شواهد counterfactual می‌گیرد** (shadow mode)، و متریک‌ها counter-metric با مالک متفاوت می‌گیرند تا گیم کردن ساختاراً گران شود.
